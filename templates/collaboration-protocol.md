# 협업 규약 (Claude · Codex) — duetcode pipeline

> 이 문서는 duetcode 파이프라인 설치 시 `docs/`에 배치되는 **협업 규약 템플릿**이다. 프로젝트에 맞게 `<...>` 자리표시자를 채우고, 저장소의 에이전트 지침 문서(`CLAUDE.md`/`AGENTS.md`)에서 이 문서를 단일 소스로 참조한다.

이 프로젝트는 **Claude(분석·설계·검증)** 와 **Codex(구현·실행)** 가 Task별로 역할을 나눠 개발한다. **진행 중인 단일 Task의 실시간 상태**만 [TASK.md](../TASK.md)의 `Active Task`에 기록한다(이 문서 = 규약, TASK.md = 현재 Task 상태). 작업 시작 시 두 AI 모두 이 규약과 TASK.md의 현재 상태를 확인한다.

## 역할 분담표

| 레인 | 담당 | 모델(예시 — 프로젝트에 맞게) |
| :--- | :--- | :--- |
| 분석·설계 | Claude | `<설계용 상위 모델>` — 넓은 컨텍스트로 전체 구조·사이드이펙트 파악 |
| 구현·실행 | Codex | `<구현용 코딩 모델>` — 의존성 고려 전면 수정 |
| 검증·리뷰 | Claude | `<검증용 상위 모델>` — 설계·docs·데이터 정합성 대조 |

특정 Task에서 다른 모델을 쓸 이유가 생기면 그 Task의 `TASK.md` `roles`에 기록한다.

**검증 레인은 옵션이 아니다.** 구현 산출물은 원래 설계와 문서/데이터 정합성 기준에 맞는지 Claude가 대조한 뒤 커밋한다.

### 하이리스크 작업 (반드시 검증 게이트 통과)

- `<틀리면 조용히 데이터가 깨지는 규칙들 — 예: 채번 카운터, 패딩 규칙, 매핑 규칙>`. 고속·저가 모델 단독 금지 — 상위 모델의 설계·검증을 앞뒤로 붙인다. `TASK.md`에 `highRisk: true`로 표시하면 lint가 `roles.designer`·`roles.reviewer`에 `Opus` 포함을 강제한다.
- **테스트 코드**: "테스트를 만들었다" ≠ "검증됐다". 실행 경로와 실제 실행 여부를 `TASK.md` 검증 결과에 기록한다.

## 핸드오프 계약 (Claude 설계 → Codex 구현)

설계를 Codex에 넘길 때 설계 산출물에 다음을 명시한다. Codex는 구현 착수 전 이 항목을 확인한다.

1. **구현 전 읽을 docs**: 작업 유형별 필독 문서.
2. **건드리면 안 되는 규칙 / 불변식**: `<프로젝트 고유 불변식>`.
3. **영향 범위**: 해당 변경이 닿는 프로파일·API·DB 스키마·파일.
4. **정합성 체크 대상**: 이 소스를 고치면 함께 봐야 할 축(docs·주석·설정·스키마).
5. **완료 조건**: 충족해야 할 동작, 허용하지 않는 회귀, 필요한 검증 명령.
6. **미확정 사항**: 추정과 확정 결정을 구분하고, 사용자 결정이 필요한 항목을 표시한다.

Codex는 설계를 맹목적으로 구현하지 않는다. 설계가 실제 코드·Git·스키마와 충돌하면 실제 상태를 우선하고 차이와 근거를 TASK.md의 `Active Task`에 기록한다. 요구사항·공개 API·DB 스키마·보안 정책을 바꾸는 수준이면 구현 전에 사용자 확인을 받는다.

## 공통 작업 규약 (양 진영 공통)

- **커밋 브랜치**: 기본 작업 브랜치는 `<기본 브랜치>`다. `main` 직접 커밋 금지(checkpoint에서 대안 분기 시에만 사용자 동의 후 별도 branch).
- **커밋 메시지**: `feat(scope): 설명` / `fix(scope): 설명` / `refactor(scope): 설명` / `docs(scope): 설명`. 하나의 논리적 변경만 담고 관련 이슈를 연결.
- **커밋 권한**: AI는 사용자가 명시적으로 요청한 경우에만 commit·push·release를 수행한다. 검증 완료가 곧 자동 커밋 권한을 의미하지 않는다.
- **응답 언어**: `<사용자 대상 언어>`. 코드·명령어·경로·기술 용어는 원문 표기 유지.
- **정합성 우선순위**: 코드·설정·데이터(실측)가 사실의 기준이며 문서·주석을 거기에 맞춘다.
- **비밀값**: 비밀값을 커밋하지 않는다.
- **사용자 변경 보존**: 작업 트리에 이미 존재하는 변경은 사용자 소유로 간주한다. Task 범위 밖 파일을 되돌리거나 덮어쓰지 않는다.
- **상태 충돌**: 이 규약과 사용자 요청이 충돌하면 사용자 요청을 우선한다. 이 규약과 실제 코드·Git·데이터 상태가 충돌하면 실제 상태를 우선하고 불일치를 기록한다.

## Task 상태머신

TASK.md의 `Active Task`는 동시에 하나만 유지한다. 최상단 YAML front matter가 기계 판독 상태의 단일 소스이며, 본문은 요구사항·근거·검증 로그를 설명한다. 상태 변경과 lint는 `npm run task -- <명령>`을 사용한다. 신규 Task는 `task start <id> --objective <목표> --requester <요청자> --designer <설계자>`로 시작한다.

```text
IDLE → DESIGN → READY → IMPLEMENTING → REVIEW → DONE
                         ↑             │
                   READY/IMPLEMENTING ←┘

진행 불가: BLOCKED
사용자 취소: CANCELLED
대안 Task로 대체: SUPERSEDED
```

- `READY`: 요구사항·영향 범위·완료 조건·필독 문서·불변식이 명확한 상태.
- `IMPLEMENTING`: Codex가 구현을 진행하는 상태.
- `REVIEW`: 구현을 마치고 Claude가 정합성 검토·검증을 수행하는 상태. 검증 결과는 REVIEW 진입 후 기록한다.
- `DONE`: 구현·정합성 검토·가능한 검증이 완료된 상태. 단순 코드 작성 완료는 `DONE`이 아니다.
- `BLOCKED`: 막힌 이유·이미 확인한 내용·사용자에게 필요한 결정을 기록한 상태.
- `CANCELLED`: 대체 Task 없이 사용자 결정으로 중단한 종결 상태.
- `SUPERSEDED`: 다른 Task·branch가 이 작업을 대체한 상태. 기록을 삭제하지 않고 대체 항목을 연결한다.

`DONE`은 검증이 `PASSED`이고 실패 수가 0이거나, 실패 수 0인 `PARTIAL`을 대화형 `approve-partial`로 승인한 경우만 허용한다. **최종 방어선은 커밋 전 사람의 `git diff TASK.md` 검토다.** `issue-sync`는 외부 쓰기이므로 사용자 명시 실행만 허용한다.

## Checkpoint와 되돌리기

`TASK.md`는 상태와 복귀 지점을 설명할 뿐 실제 코드 snapshot을 저장하지 않는다. 복귀 가능한 코드 상태는 Git commit 또는 별도 branch로 남긴다.

- 설계가 `READY`가 되면 `designCheckpoint`에 commit SHA를 기록한다. 사용자가 commit을 요청하지 않았다면 `미생성(사용자 승인 필요)`로 기록한다.
- 코드도 분기할 때 checkpoint commit에서 새 branch를 만든다. 기존 Task와 branch는 보존한다.
- 공유된 commit을 취소할 때는 이력을 지우는 `reset`보다 `git revert <commit>`을 우선한다.
